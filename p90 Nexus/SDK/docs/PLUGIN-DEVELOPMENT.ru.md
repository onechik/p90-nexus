# Разработка плагинов

## Первый проект за один цикл

В комплекте открой `SDK`. Используется .NET SDK **10.0.401**, закреплённый в `global.json`, а создаваемая DLL нацелена на **net6.0**. Это разные вещи: SDK собирает код, встроенный в загрузчик runtime **6.0.7** его исполняет. Для запуска готового плагина SDK не нужен. На машине автора `dotnet --list-sdks` должен показывать 10.0.401; для первого restore нужен доступ к nuget.org или уже заполненный кэш reference packs 6.0.36.

Из папки комплекта `P90 Nexus`:

```powershell
.\SDK\New-Plugin.ps1 -Name OnechikHello -Id onechik.hello -Destination 'D:\MyPlugins\OnechikHello'
& 'D:\MyPlugins\OnechikHello\Build.ps1'
```

Если политика PowerShell запрещает скрипт, запусти отдельную консоль командой `powershell.exe -NoProfile -ExecutionPolicy Bypass` и выполни команды в ней. Постоянную политику менять не требуется. Каталог назначения должен быть новым: генератор не перезаписывает проект.

`Name` — имя сборки/пространства имён, 3–40 латинских букв и цифр, первая буква заглавная. `Id` — устойчивый уникальный ID, например `author.plugin`; не переименовывай его при каждом обновлении, иначе сменятся конфиг и журнал.

Созданы `Plugin.cs`, `Plugin.csproj`, `lib/P90.API.dll`, `Build.ps1`, `NuGet.Config`, `global.json`. Проект самостоятелен: можно переместить папку целиком. Ссылок на исходники ядра, Unity или игру нет. Готовая DLL: `bin/Release/net6.0/OnechikHello.dll`.

Закрой игру, создай `<игра>/P90/plugins/OnechikHello`, скопируй туда **OnechikHello.dll** и запусти игру. Для распространения передавай папку OnechikHello целиком с инструкцией; пользователь просто помещает её в P90/plugins. Дополнительные управляемые DLL можно положить рядом с DLL плагина; зависимости загружаются в общий runtime, разные версии не изолируются. Не копируй вторую P90.API.dll: её предоставляет ядро. Из папки игры:

```powershell
.\scripts\P90.ps1 p90.plugins | Format-List
.\scripts\P90.ps1 onechik.hello.hello | Format-List
.\scripts\P90.ps1 onechik.hello.status | Format-List
```

Ожидается Active и `Hello, Onechik!`. Для объявления создай собственный сервер, дождись персонажа:

```powershell
.\scripts\P90.ps1 -Command onechik.hello.announce -Arguments 'Привет от плагина!' | Format-List
```

## Как читать исходник шаблона

`[Plugin(...)]` объявляет идентичность и совместимость. Класс `ExamplePlugin` реализует Start и Stop. Start сохраняет новый контекст, сбрасывает счётчик, читает Settings, создаёт три команды и две подписки. Конструктор ничего не делает с игрой.

Команда `.hello` возвращает текст из Settings, `.status` показывает серверный флаг и счётчик наблюдений, `.announce` использует Broadcast. Счётчик `observedPlayers` — накопленные наблюдения доступности с момента Start, включая начальный снимок, а не текущее число игроков. Точный список — `context.Server.Snapshot.Players`.

Stop записывает сообщение и освобождает свою ссылку на контекст. Ядро снимет регистрации, созданные через контекст. Файлы, потоки, таймеры, внешние подписки и другие ресурсы, созданные самостоятельно, освобождает плагин.

Для маленького нового плагина достаточно заменить содержимое Plugin.cs следующим кодом (в сгенерированном проекте имя сборки может остаться прежним):

```csharp
using P90.API;

[Plugin("onechik.counter", "Player counter", "1.0.0")]
public sealed class CounterPlugin : IP90Plugin
{
    public void Start(IPluginContext context)
    {
        context.Commands.Register("onechik.counter.count", _ =>
        {
            var snapshot = context.Server.Snapshot;
            if (!snapshot.Supported)
                return CommandResult.Fail(snapshot.DisabledReason);
            if (!snapshot.IsServer)
                return CommandResult.Fail("Сначала создай свой сервер.");
            return CommandResult.Ok($"Готовых персонажей: {snapshot.Players.Count}");
        });
    }

    public void Stop() { }
}
```

Этот пример не меняет мир, не отправляет сетевые сообщения и не требует собственного состояния. Проверка: `.\scripts\P90.ps1 onechik.counter.count`. При замене примера в той же DLL полностью перезапусти игру; команда p90.restart не перечитает бинарник.

## Конфиги и ввод пользователя

Чтобы команда появилась в справке с объяснением, добавь при Register именованные аргументы `description: "Что делает команда"` и `usage: "имя.команды Пример аргументов"`. Полный пример — в [справочнике API](API.ru.md). Обновлённый шаблон SDK уже заполняет эти строки для каждой команды. Владелец показывается автоматически по ID плагина. После изменения текста нужно пересобрать DLL и перезапустить игру, как при любом изменении кода.

Вынеси изменяемые значения в класс настроек с публичными свойствами. Читай один раз в Start, проверяй допустимость значений. Для обновления конфигурации удобно `p90.restart <id>`, если твой Start снова вызывает Load. Ядро не выполняет миграцию старых настроек автоматически. Для сложной схемы добавь собственный `SchemaVersion` и явный переход между версиями, сохрани резервную копию перед миграцией.

Аргументы команды приходят строками. Проверяй число аргументов, используй `TryParse` и явную культуру для чисел, возвращай понятный Fail. Не используй исключение как обычный ответ оператору. Не составляй из непроверенного ввода пути или shell-команды. Начинай имена команд с ID плагина; все имена общие для процесса.

В событиях сервера начальное состояние не воспроизводится автоматически: получи Snapshot при Start, а затем слушай изменения. На ServerStopped очищай состояние сессии. На повторном Start сбрасывай всё временное: объект плагина тот же.

## Периодическая работа и ошибки

Для редких проверок можно подписаться на CorePulse. Сравнивай `Stopwatch.Elapsed` с собственным дедлайном, если нужно время; Number — счётчик вызовов, не секунды. Не отправляй сообщение каждый импульс без условия и не рассчитывай на точную частоту. Во время загрузки кадры могут задерживаться.

Обработчики должны быстро завершаться: медленная работа блокирует игру. Core перехватывает обычные синхронные исключения обработчика, пишет лог и продолжает dispatch. Бесконечный цикл, нативное падение, огромные выделения памяти и async void этим не изолируются. Все плагины работают в одном процессе и AssemblyLoadContext.

Если Start завершился частично и упал, Stop всё равно может быть вызван: проверяй null и освобождай только созданные ресурсы. Сохраняй токены Register/Subscribe лишь когда нужна досрочная отмена; Dispose вызывай на основном потоке.

## Зависимости и совместимость

Обычный плагин использует только P90.API. Не включай в поставку P90.Core, P90.Loader, Unity или Mirror. Сторонний NuGet-пакет не становится доступным в игре от одного PackageReference: его runtime-зависимости нужно отдельно проверить и документировать. У загрузки нет гарантированного разрешения произвольного дерева зависимостей и изоляции версий; предпочтительна небольшая DLL без сторонних runtime-зависимостей.

Прямая ссылка на Assembly-CSharp/IL2CPP привязывает плагин к внутренностям конкретной игры и обходит границу стабильного API. Для общей функции предпочтительно расширить адаптер и публичный контракт по руководству ядра. Нельзя обещать изменение роли или предметов только на основании наличия имени метода в метаданных.

## Проверка и передача плагина

Передай автору сервера DLL, ID/версию, требуемый API major и сборку игры, список команд, настройки, зависимости, способ удаления и ограничения. Проверь Start, Stop, повторный Start, неверный JSON, меню без сервера, действующий хост и остановку сессии. Сетевые изменения проверяй на чистом клиенте отдельного компьютера.

После ошибки читай `P90/logs/<id>.jsonl`, после ошибки загрузки — `P90/logs/core.jsonl` и журнал BepInEx. Для обновления: закрыть игру → собрать → заменить DLL → запустить → проверить команды. Конфиги сохраняются; совместимость схемы обеспечивает автор.

Подробные сигнатуры и граничные случаи — в [API](API.ru.md). Полный исходник примера доступен в SDK/template и SDK/examples/OnechikHello.
