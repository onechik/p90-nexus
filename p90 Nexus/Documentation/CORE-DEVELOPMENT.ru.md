# Изменение ядра и адаптера

## Карта проекта

```text
winhttp.dll (UnityDoorstop)
  → BepInEx IL2CPP + встроенный CoreCLR
    → P90.Loader: Unity-компонент, загрузка, Update, завершение
      → P90.Core: плагины, области ресурсов, команды, события, конфиги
      → P90.GameAdapter: проверка сборки и доступ к игре
        → штатный Mirror RPC → обычные клиенты
P90.API: контракт между ядром, адаптером и плагинами
```

| Файл/проект | Ответственность |
| --- | --- |
| P90.API/Contracts.cs | Атрибут, IP90Plugin, контекст, команды, CorePulse |
| P90.API/Game.cs | Снимки, серверный интерфейс, игровые события |
| P90.Core/PluginHost.cs | Discovery, состояния, scope, обработчики и файлы |
| P90.Core/ServerTracker.cs | Чистое сравнение снимков и создание событий |
| P90.Core/LocalControl.cs | Локальный mailbox и встроенные команды |
| P90.GameAdapter/BuildGuard.cs | Проверка шести файлов игры по SHA-256 |
| P90.GameAdapter/GameServer.cs | Чтение Mirror/Unity, Broadcast, отключение адаптера |
| P90.Loader/CoreLoader.cs | BepInEx entry point, Poll/Publish/Tick/Control, журнал запуска |
| P90.Loader/AdapterTest.cs | Диагностические сценарии игрового адаптера |
| P90.Core.Tests | Проверки ядра без Unity, включая BuildGuard |
| P90.SdkVerifier | Проверка независимого примера через публичный API |
| P90.Samples.* | Три технических плагина для разработки |
| P90.BootstrapProbe / P90.GameBaseline | Исследовательские диагностики, не штатная поставка |

## Подготовка рабочего дерева

Используй отдельную законно установленную копию поддерживаемой игры. Установи Nexus и запусти один раз: появится BepInEx/interop. Закрой игру. Из `Development` комплекта скопируй **src и scripts в корень этой рабочей копии**, а из `SDK` — содержимое в каталог `sdk`. Development сам по себе не является game root. Скрипты и HintPath проектов рассчитаны на структуру `<игра>/src/<проект>` и `<игра>/BepInEx`.

Изменяй только свою рабочую копию. Исходные файлы игры в комплект не включены. Для P90.API/P90.Core не нужны Unity-типы; для Loader/GameAdapter нужны локально сгенерированные interop и библиотеки загрузчика. Dummy DLL с пустыми телами не восстанавливают реальную логику игровых методов.

Используемый инструмент сборки — SDK 10.0.401. В SDK-проекте он закреплён; Build-Core использует доступный `dotnet` и сам версию не фиксирует. Перед сборкой проверь `dotnet --version`, не смешивай непроверенные инструменты с release-артефактами.

```powershell
# Из корня рабочей игры. Сборка и тесты, без установки DLL:
.\scripts\Build-Core.ps1
# Обновить SDK и проверить отдельный генерируемый проект:
.\scripts\Build-Sdk.ps1
.\scripts\Test-Sdk.ps1
```

Результаты сборки лежат в src/*/bin/Release/net6.0. Build-Core строит Core.Tests и Loader, а связанные проекты — по ProjectReference. Сначала выполняются тесты, затем возможна установка по явному `-Deploy`. Этот режим копирует четыре системные DLL **и все три технических плагина**; он предназначен для разработки. Он не является установщиком выпуска с одним образцом и не создаёт полный откат. Сохрани предыдущие системные DLL до его применения.

## Инварианты ядра

PluginHost создаётся на потоке, который затем обслуживает все операции. Discovery сканирует только *.dll в корне plugins, сортирует пути и типы Ordinal, загружает в AssemblyLoadContext.Default. Атрибут проверяется до конструктора. Графа зависимостей плагинов, приоритетов загрузки и изоляции сборок нет.

Переходы: Stopped → Starting → Active; ошибка Start → попытка Stop → Faulted; Active → Stopping → Stopped. StopAll идёт в обратном порядке загрузки. Scope владеет HashSet регистраций; их Dispose снимает обработчик и убирает токен из HashSet. При полной очистке берётся копия коллекции, чтобы удаление не испортило обход. Не возвращай накопление уже освобождённых токенов.

Dispatch использует снимок списка подписок, проверяет enabled и активность владельца; исключение одного callback не мешает остальным. Синхронная запись логов может влиять на кадр: избегай высокочастотного шума. Ошибки файлового лога пытаются уйти в sink, сам sink не должен нарушать lifecycle.

Loader в Update сначала опрашивает адаптер и публикует изменения, затем примерно раз в 0.1 секунды обслуживает control, затем диагностический сценарий; импульс ядра — примерно раз в секунду. При ошибке адаптера он отключается. При необработанной ошибке основного цикла control и плагины останавливаются; selftest завершается кодом 1. При штатном выходе снимаются ресурсы. Проверять только exit code недостаточно: диагностический auto-exit может иметь код 0, а проблему видно в журнале.

## Файловый протокол управления

`P90/control/session.json`: Session (GUID N), ProcessId, ProcessStartedUtc, UpdatedUtc, Ready. GUID control-сессии не равен SessionId игрового сервера. Heartbeat обновляется примерно раз в секунду при Poll; Dispose ставит Ready=false.

Запрос: UTF-8 JSON `inbox/<Id>.json` с полями `Id`, `Session`, `CreatedUtc` в UTC ISO 8601, `Command`, `Arguments` (массив строк). Писатель создаёт временный файл, затем переименовывает в .json. Poll берёт до четырёх файлов за вызов, переименовывает в .processing, проверяет, исполняет, пишет `replies/<Id>.json` (`Id`, `Success`, `Message`) и удаляет захваченный запрос. Очерёдность файлов не является гарантированным FIFO.

Ограничения: 16 KiB, до 64 аргументов, возраст до 30 секунд и не более 5 секунд в будущем, точное совпадение GUID/имени файла/сессии. До 10 000 учтённых ID на процесс. Синтаксически допустимый ID учитывается до проверки аргументов; повтор запроса не должен исполняться повторно. Ответы не удаляются автоматически. Файл с именем, не являющимся GUID N, пропускается. После аварии могут остаться .processing; это диагностический след, не гарантия автоматического восстановления.

Это не транзакционный протокол exactly-once: падение между исполнением и записью ответа не позволяет клиенту узнать результат. Для важных будущих операций проектируй идемпотентность на уровне операции. Таймаут PowerShell не отменяет запрос. Защита от старого PID использует путь EXE и UTC времени старта с допуском 2 секунды; обе даты нормализуются в UTC для совместимости PS5.1/7.

## Как добавить возможность игры

1. Сформулируй наблюдаемое поведение и требуемую серверную авторитетность. Определи, что увидит чистый клиент, нужны ли сохранение состояния и позднее подключение.
2. Найди настоящую реализацию в конкретной сборке: метаданные дают имена/адреса, машинный код и runtime-наблюдения подтверждают действие. Зафиксируй адреса, hash сборки и смысл аргументов.
3. Проверь, что существующая сеть игры умеет передать эффект чистому клиенту. Не вводи новое сообщение/тип, которого клиент не понимает. Не доверяй только локальной картинке хоста.
4. Добавь минимальный контракт P90.API без Unity/IL2CPP-типов; опиши ограничения и результат отказа. Реализацию игровых обращений держи в GameAdapter.
5. Снова проверяй активную серверную роль непосредственно перед изменением игры, работай на Unity-потоке, не сохраняй объекты сцены после её смены. При неподдерживаемой сборке отказывай до игровых обращений.
6. Добавь модельные проверки переходов/валидации, затем реальный локальный тест и сценарий чистого клиента. Только подтверждённое поведение внеси в документацию.

Текущий Broadcast вызывает `PlayerAdmin.cfh` (исследованный wrapper RpcDoBroadcast, RVA 0x340A40 этой сборки). Выбирается один объект, видимый всем готовым соединениям, и вызывается один RPC. Не умножай вызов на количество игроков. Имена вроде `NetworkServer.lon`, `NetworkClient.njo`, `llq` обфусцированы и не являются устойчивым API.

## Обновление игры и API

Новая игра → новый отпечаток → новое исследование изменённых методов → interop этой игры → сборка → локальные и сетевые тесты. **Одна замена SHA-256 в BuildGuard не переносит адаптер.** Обнови также supported-game.json поставки и таблицу поддержки. При ошибке сборки/адаптера должен сохраняться отказ, а не попытка работать наугад.

Breaking change контракта требует нового major и согласованного обновления PluginHost.ApiMajor, SDK, примеров, документации и миграции плагинов. Даже добавление метода в интерфейс может нарушить сторонние реализации: оценить бинарную совместимость необходимо отдельно. Обновление набора DLL делай согласованно, при закрытой игре. Не меняй ID плагинов/загрузчика без причины и не выдавай новый контракт за старый major.

## Отладка и границы

Сопоставляй журнал BepInEx, core.jsonl запуска и JSONL плагина по UTC/PID. Обычные CLR-исключения и нативное падение — разные случаи. При подозрении на игровую ошибку сравни с чистой копией либо отдельно подготовленной baseline; отсутствие ядра при оставшемся BepInEx — не полностью немодифицированная игра. Ранее GuitarItem.Update в Sandbox воспроизведён без P90 Core/Adapter/плагинов, но это не доказательство причины всех будущих исключений.

Dedicated и `-batchmode` не подставляй вместо обычного запуска для ускорения теста: игра меняет режим работы. Не публикуй игровые DLL/декомпилированные данные вместе с собственными исходниками. Процедура выпуска и нужные проверки — в [RELEASE](RELEASE.ru.md).
